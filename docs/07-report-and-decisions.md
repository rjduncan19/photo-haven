# 07. Report and decisions

The report is where the human decides. It is folder-centric because that's where the big wins are ("this whole backup folder is redundant"), with file-level detail for leftovers.

## 1. Form

- A **static report directory** generated by `photohaven report`, opened in Edge or Chrome from disk. No server, no build step, vanilla JS.
- `index.html` holds the summary and the folder table. Per-folder detail lives in `detail/<n>.js` shards, loaded on demand by inserting a `<script>` tag. That works over `file://`, where `fetch()` of local JSON is blocked. It also keeps the main page fast: the full per-file detail for 300k files would be tens of MB.
- Decisions persist in `localStorage`, keyed by `report_id`, so closing the tab loses nothing. **Export** downloads `decisions-<report_id>.jsonl` ([03 §5.3](03-format-spec.md#53-decisions-export-file-from-the-report)).
- Thumbnails: ExifTool extracts the *embedded* preview (`-b -ThumbnailImage`, or `PreviewImage` for raws) into local state `thumbs/<sha256[:2]>/<sha256>.jpg`. No image decoding, so HEIC thumbnails cost nothing extra. Up to 6 sample thumbnails per folder row, more on the detail view. Thumbnails stay in local state, never in OneDrive.

**Considered and deferred:** a localhost server (`photohaven serve`) would let decisions go straight into the log with no export/import step, and could load detail via `fetch`. It's a better UX and likely the v2 direction, but the handoff chose the static page with export, and the static page is simpler to make safe. The export format is the same either way.

## 2. Statistics computed per folder

For folder *F* (files directly in it, `present` only):

| Stat | Definition |
|---|---|
| `files`, `bytes` | Count and total size |
| `dup_files`, `dup_bytes` | Files whose `sha256` has ≥ 1 other present instance anywhere |
| `unique_files` | Files with no other instance (these block a "fully redundant" verdict) |
| `unhashed_files` | Files with no `sha256` yet (cloud-only, skipped, `other` media, or pass 2 pending) |
| `redundant` | `dup_files == files` and `unhashed_files == 0` |
| `reclaimable_bytes` | Bytes freed if *F* is marked `remove`: equals `dup_bytes`, since its unique files stay (last-copy invariant). Only an upper bound when two folders that share content are both marked remove, because one copy of each group must stay. |

Also computed per **subtree** (F and all descendants), since "Backup 2019" is usually a tree.

**Refinement (M2):** "duplicate" here means *a copy outside this folder* (outside the subtree, for subtree stats). Copies that exist only inside one folder (`IMG_1 - Copy.jpg` next to `IMG_1.jpg`) don't make the folder removable as a whole, since one of them must stay; they are counted as `internal` and listed in their own section with file-level suggestions. A folder's `reclaimable_bytes` is its outside-copy bytes plus those internal extras. Non-photo files (`other` media) count as unhashed, so they block `redundant`; the suggestion says so ("a remove decision moves only the duplicates").

For folder **pairs** *(A, B)* sharing at least one content, via an inverted index `sha256 → folders` (only groups with instances in ≥ 2 folders are touched, so this stays cheap):

| Stat | Definition |
|---|---|
| `shared` | Distinct contents in both A and B |
| `a_in_b` | Fraction of A's contents also in B |
| `b_in_a` | Fraction of B's contents also in A |
| `contained` | A ⊆ B (`a_in_b = 1`) |
| `identical` | A ⊆ B and B ⊆ A |
| `shared_bytes` | Sum of sizes of shared contents |

## 3. Report layout

1. **Summary.** Files, bytes, duplicate groups, total reclaimable bytes (`dup_groups.reclaimable`), cloud-only and unhashed counts, scan time, hash pass completed (`candidates` or `all`), and machines whose facts are included.
2. **Easiest wins: folders contained in another folder.** Every folder A with `contained` in some B, sorted by `reclaimable_bytes` descending. Each row: A's path, size, file count, *contained in* B (and how many other folders), sample thumbnails, suggestion, dropdown.
3. **Fully redundant folders.** `redundant` but spread across several folders rather than contained in one. Same row layout, plus "copies live in: X (60%), Y (40%)".
4. **Heavy overlap.** Pairs with `a_in_b ≥ 0.5` that aren't contained. Shows what's unique in each.
5. **Content-equivalent groups** (same picture, different metadata) — report only.
6. **Warnings.** Pairs that a removal would split (raw/JPEG, Live Photo), orphan Live Photo videos, cache conflicts, errors, orphaned decisions (targets that no longer exist).
7. **All folders**, collapsible tree with subtree totals, for browsing and file-level decisions.

Folder detail (from a shard): each file with thumbnail, size, date taken, and "other copies at: …". Each file row has its own dropdown; file-level decisions override the folder's.

## 4. Suggestions

Every row comes pre-filled with a suggestion and a one-line reason. **Suggestions are never decisions**: nothing applies until it's in an exported decision.

| Situation | Suggestion | Reason shown |
|---|---|---|
| Folder is intake or protected | `keep` (locked; dropdown disabled at folder level) | "Camera Roll is protected intake" |
| A contained in B; A is generic (`Backup`, `Imports`, `(1)`, `- Copy`), B is not | A: `remove` | "Every file is in B; A's name is generic" |
| A contained in B; B is intake | A: `remove` | "Every file is already in the camera roll" |
| A and B identical; names differ in descriptiveness | Less descriptive: `remove` | "Identical to B, which has the more descriptive name" |
| A and B identical; equally descriptive | Shallower or older-created: `keep`; other: `remove` | "Identical; keeping the one at …" |
| `redundant`, spread across folders | `remove` | "Every file exists elsewhere" |
| Partial overlap | `undecided` | "N files are unique to this folder" |
| Unique files only | `keep` | — |

The descriptive-name comparison uses the rules in [05 §7](05-file-relationships.md#7-folder-names-and-event-guesses). The suggestion engine is a pure function of DB state, unit-tested against a table of scenarios.

**Refinements (M2), from the M0 corpus:**

- **Path descriptiveness.** Names are compared by the most descriptive name on the folder's path, then its own: `Pictures/iPhone/2026-10` is described by `iPhone`, so it beats `Backup 2026 (phone)` even though `2026-10` itself is generic.
- **A descriptive folder contained in a less descriptive one is kept** ("every file is also in B, but this folder's name says more"). `Hawaii trip` inside a big `Backup 2019` should not be the copy that goes.
- **Easiest wins lists only folders suggested for removal.** Contained folders suggested for keeping stay in the tree.
- **Redundant trees.** A subtree removal is suggested only when every folder with files in the tree would itself be suggested for removal, so folder and tree suggestions never disagree; only the top-most such tree is listed.
- **Coherence.** After the per-folder rules, if every folder holding some content is suggested for removal, the best-ranked of them is suggested for keeping instead. Accepting every suggestion therefore never asks to remove every copy. The planner enforces the last-copy invariant anyway ([08 §2](08-apply-quarantine-verify.md#2-choosing-keepers)); this keeps the suggestions honest.
- **Accept suggestions** per section turns the shown suggestions into decisions in one click; nothing is exported until the human clicks Export.

## 5. Resolving effective decisions

For an instance at `(root_id, relpath)` with content `sha256`, in phase `dedupe`, the effective action is chosen in this order:

1. **File decision** whose target path matches *and* whose `target.sha256` equals the instance's current `sha256`. A file decision about different bytes doesn't apply.
2. **Folder decision** with `scope = folder` on the instance's own folder.
3. **Subtree decision** on the nearest ancestor folder (deepest first).
4. Otherwise `undecided`.

Within one level, the latest record by `(at, machine_id, seq)` wins, and `undecided` at that level means "no decision here; fall through to the next level."

**Protected folders** (intake, `protected_folders`): folder and subtree `remove` decisions are ignored for instances inside them, and reported as ignored. Only a file-level `remove` can quarantine an instance from the camera roll (for example, a duplicate *within* the camera roll from a repeated upload).

`photohaven decisions show-effective <path>` prints the chain for any instance, to make the resolution debuggable.

## 6. Round trip

```
report (report_id R, from scan S)
   └─ human edits dropdowns → localStorage
   └─ Export → decisions-R.jsonl
photohaven decisions import decisions-R.jsonl   (or: photohaven plan --decisions decisions-R.jsonl)
   └─ validates header (library_id matches, report_id known)
   └─ warns if newer scans exist than S (state may have changed since you reviewed)
   └─ appends to logs/decisions.<m>.jsonl, skipping duplicates
photohaven plan
   └─ dry run (08)
```

A stale report is not dangerous, because every file decision pins `sha256` and every move re-checks the disk. It can be confusing, though, so the plan output lists decisions whose targets have changed since the report was generated.
